# Is a true RTT / PIP camera feed possible in SE2?

**No — not through the managed API, and not by patching around it.** The engine can
render 2D into an offscreen target, and the LCD panel system already does exactly
that. It cannot render the *3D scene* into one. There is no second view, no
camera-to-target entry point, and nothing to hook that would create one.

Evidence below is from `docs/rtt-recon.md`, generated by `tools/RenderRecon`
against build assemblies in the SE2 install. Regenerate with `dotnet run` from
that folder after a game patch — the verdict is only as current as the build.

## What a true RTT camera would need

Three things, in order. The chain breaks at step 2.

1. **An offscreen render target.** ✅ Exists.
   `RenderContracts.CreateOffscreenTarget(name, resolution)` returns an
   `OffscreenRenderTarget` with a `TextureHandle`. The LCD system already borrows
   these per panel surface via `LcdRenderTargetPoolSessionComponent.Borrow`.

2. **A way to render the scene from a second camera into it.** ❌ Absent.

3. **A way to get that texture onto the panel.** ✅ Exists — the LCD material path
   (`SetNewScreenMaterialHandle` → `CreateRuntimeLcdMaterial`) already binds an
   offscreen target's handle to the panel's material.

The bookends are in place. The middle does not exist.

## Why step 2 is absent

### Offscreen targets are a 2D-only surface

Every consumer of an offscreen target in the shipped assemblies:

| Consumer | What it does |
|---|---|
| `LcdRenderTargetPoolSessionComponent.Borrow` / `Return` | pools them for LCD panels |
| `UIStage.OffscreenUIRenderer.DrawOne` | clears the RT, replays **UI batches**, mipmaps, copies |
| `Utils.OffscreenTargetManager` | bookkeeping for screenshot-to-memory |
| `UISystem.CreateImmediateBatchFor` / `CreatePersistentBatchFor` | points a **2D draw batch** at one |

`OffscreenUIRenderer.DrawOne` is the only thing that draws into an offscreen
target, and its call sequence is `UISystemComponent.RecordBatches` →
`UIBatcher.BeginDraw` → `IUIBatch.Draw`. That is the UI batcher: `DrawFill`,
`DrawImage`, `DrawString`, `DrawPath`. No geometry, no scene, no depth.

### The scene has exactly one view, and it is not settable

The 3D scene renders from a single `RenderView` held in
`Render12.Core.Systems.SettingsManager._renderView`. The public property has
**no setter** (`RenderView`, `PreviousRenderView`, `FreezedRenderView` — all
getter-only).

Other `RenderView` instances do exist, which is the tempting part. They are all
internal to lighting:

- `LocalLightsManager.DepthUpdateRequest.View` / `ShadowMaskUpdateRequest` — shadows
- `CascadeUpdateInfo.RenderViewSlim` — shadow cascades
- `EnvironmentProbeManager.Render.View` — IBL probes
- `WaterMeshJob.GetSunRenderView` / `GetCrossSectionRenderView` — water

None produce a colour image into a caller-supplied target. They feed depth,
shadow masks and irradiance back into the one main view.

`SceneDrawSystem.DrawRenderViewFrustum(RenderView&)` is a debug frustum
visualiser, not a scene render. `CameraSettings.EnableCompositeRenderView()`
reads like the exception but is called from exactly one place —
`SceneDrawSystem.RenderLocalLightShadows` — so "composite" there is about shadow
accumulation, not compositing two camera views.

### The render contract has no per-view entry point

`RenderSystem` exposes global toggles only — `SetDraw3DScene(bool)`,
`SetDrawUI(bool)`, `SetDisplaySettings`. `RenderContracts` is ~60 `Create*Entity`
methods (models, lights, decals, particles, water, flora) plus
`CreateOffscreenTarget`. Nothing takes a camera and a target.

### The main target cannot be sampled

`MainRenderTarget`'s entire public surface is:

```
Task TakeScreenshotAsync(FileHandleWritable saveFile, Vector2I? downsampleResolution,
                         BoundingBox2I? viewport, bool withoutUi, bool awaitWrite)
```

Async, to a **file**. Not a texture you can bind per frame.

### Environment probes are not a back door

Worth ruling out explicitly, since they are the one system that genuinely
rasterises the world from a chosen point. `EnvironmentProbeManager` holds exactly
two cubemaps — `CloseEnvProbe` and `FarEnvProbe` — both centred on the player
camera, driven by `PrepareProbes()` on a slow state machine (`MAX_STATE_COUNT`,
blend weights), for image-based lighting. They are not placeable: outside
`VRage.Render12` the only references are to the `EnvironmentProbeSettings`
struct, through serialiser and clone plumbing. The manager itself is unreachable.

The hologram pass is likewise a dead end: `HologramSettings` is material/shader
configuration, not a scene-to-texture pass.

## Could the scene pipeline be re-entered anyway?

This is the real question, so it got its own pass rather than a judgement call. A
second 3D view needs two things to be true. **(a)** the view the stages read must
be swappable, and **(b)** the targets the stages write must be redirectable.

### (a) The view — one seam, but ~80 consumers

`SettingsManager.SetCameraParameters` is the *only* method that writes the view
outside the constructor and frame-end bookkeeping. So there is a seam.

It is not a usable one. Roughly 80 methods read `SettingsManager.RenderView`, and
many carry **state across frames**: FSR3 upsampling history, texture streaming
priorities (`ManagedTexturePrioritizerComponent`), shadow cascade caches
(`CascadeShadowsContext.CheckCameraShifted`), environment probe blending,
raytracing TLAS construction, culling capacity tracking. Swapping the view
mid-frame doesn't produce a second picture; it corrupts the first one's temporal
state.

### (b) The targets — one seam, and it is a static field

An earlier draft of this document said there was no seam here. That was wrong.
The scene's buffers live in a single frame-global
`Render12.Core.Systems.ScreenBuffers`:

```
ResizableDepthStencilTexture    DepthStencilBuffer     // one
ResizableRWRenderTargetTexture[] GBuffer               // one set
ResizableRWRenderTargetTexture   FinalLDRTexture       // one
Vector2I PreUpscaleResolution / PrevPreUpscaleResolution
int _cameraJumpWaitFrameId, _screenshotWaitFrameId
```

One depth buffer, one G-buffer set, one LDR output, carrying frame-sequenced
temporal fields. The draw stages do not receive a target as a parameter — they
read it from this global.

That *is* the seam, and with plugin-level access it is reachable:

- it is held in exactly one place, `Keen.VRage.Render12.Core.CoreSystems.ScreenBuffers`,
  a **public static field** — writable by reflection
- `ScreenBuffers` has a **public parameterless constructor** and an internal
  `InitializeBuffers(Vector2I&)`, so a second instance can be built and sized
- `SettingsManager.SetCameraParameters` is the single writer of the view

So "swap the global, point the camera, re-run the passes, swap back" is a
coherent plan, not a fantasy.

### The existence proof: the engine already does this

The strongest argument that it is possible is that the renderer re-runs its own
scene passes from other viewpoints, into other targets, every frame:

```
SceneDrawSystem.ExecuteEnvironmentProbeUpdate   [GeometryStage, LightingStage, PostProcessStage, PrepareStage]
SceneDrawSystem.RenderShadowCascades            [GeometryStage, LightingStage, PrepareStage]
SceneDrawSystem.RenderCharacterShadows          [GeometryStage, LightingStage, PrepareStage]
```

The stage machinery is therefore **not hard-wired to the main view**. It is
already re-entrant for probes and shadows. A camera feed is the same shape of
problem: geometry, from a chosen viewpoint, into a target that is not the screen.

`SceneDrawSystem` also exposes the passes discretely — `DrawUnlit`,
`RenderTransparent`, `RenderHolograms`, `ExecuteVolumetricPasses`, `DrawUI` — so
a second pass can be assembled from parts rather than by re-entering the whole
frame.

### What still makes it hard

Possible is not cheap. In rough order of how likely each is to sink an attempt:

1. **Global state, ~50 managers.** `CoreSystems` holds them all statically. Most
   are device-level and view-independent (shaders, PSOs, heaps, samplers,
   descriptor tables) and need no copy. A handful are frame- or view-scoped and
   would have to be saved/restored or duplicated: `FrameSpan`, `FrameDispatcher`,
   `GPUFrameManager`, `DrawContextManager` contexts, `HierarchicalContainer`
   culling state, `ManagedTexturePrioritizer` / `ManagedTextureStreaming`,
   `RayTracingScene`. Sorting out which is which is the bulk of the work.
2. **Temporal effects.** FSR3 upscaling, SSR and shadow-cascade caching keep
   per-view history. Running a second view through them corrupts both pictures
   unless the history is isolated — or unless the second pass simply skips them,
   which is the pragmatic answer for a camera feed.
3. **GPU cost.** A second full scene pass is a second frame's worth of GPU work.
   Mitigable and probably must be: low resolution, low refresh rate, no
   post-processing. A 256×256 unlit feed at 10 Hz is a different proposition from
   a full second view at 60 fps.
4. **Stability surface.** This all runs on the render thread against internal,
   version-unstable APIs. Mistakes are hard crashes, and D3D12 errors can escalate
   to device removal.
5. **Patch fragility.** Every SE2 update can move these internals.

### The remaining public channel

`RenderSystem.OpenRenderCommandBuffer()` / `SubmitRenderCommandBufferAsync()` is
the only other way into the renderer. It carries the `*_Impl` contract calls
already enumerated above — create entity, create offscreen target, update
definitions. There is no "draw the scene from here to there" command to put on it.

**Temporal multiplexing — move the camera on alternate frames.** Mechanically
possible: `CameraComponent.SetTransformOverride` exists and
`CameraSystemComponent.RenderCameraEntity` has a setter. Useless in practice —
the view being moved is the player's own, so they would see the feed instead of
the cockpit, at half frame rate. It cannot produce a *simultaneous* second view.

**Screenshot the main target and blit it.** `TakeScreenshotAsync` is file-backed
and asynchronous. Even ignoring the round trip through disk, it captures the
player's own view, which is not a camera feed.

## What would have to change

The missing piece is small to describe and entirely on Keen's side of the line —
a scene render entry point that takes a camera and a target, roughly:

```
void RenderSceneTo(OffscreenRenderTarget target, in RenderView view);
```

For that to be implementable at all, the engine needs per-view `ScreenBuffers`
rather than one global set, and per-view temporal state for FSR3, shadow cascades
and texture streaming. That is a real piece of renderer work, not an API veneer —
which is worth knowing, because it means the feature is unlikely to appear as a
side effect of the mod API landing.

Two things would change the verdict, and both are worth watching for:

- **A public mod API that exposes a per-view scene render.** Re-run
  `tools/RenderRecon` after any patch; probes 16–20 target exactly this.
- **In-game security cameras / camera blocks shipping in SE2 itself.** If Keen
  builds that feature, the per-view plumbing has to exist, and it becomes
  reachable. Its absence today is consistent with the single-view architecture
  found here.

## Bottom line

Two different answers, depending on the access you have.

**Through the public/managed API surface: no.** There is no scene-to-target
entry point, offscreen targets are a 2D-only surface, and nothing in
`RenderContracts` or `RenderSystem` takes a camera and a target.

**With plugin-level access — Harmony on internals, reflection onto private
state: yes, in theory.** The view has a single writer, the target set is a single
public static field, `ScreenBuffers` can be constructed and sized independently,
and the engine already re-runs its scene passes from other viewpoints into other
targets for environment probes and shadow cascades. The machinery is re-entrant;
it is the *bookkeeping* around it that is single-view.

That makes this a hard engineering project rather than an impossibility. The
honest estimate is that the difficulty is concentrated in one place: working out
which of the ~50 `CoreSystems` globals are view-scoped and must be saved,
restored or duplicated around a second pass. Everything else follows from that.

> **Superseded in part.** Reading the probe path settled this — see
> [`attack-plan.md`](attack-plan.md). `ExecuteEnvironmentProbeUpdate` mutates no
> globals at all: the camera is a transient constant buffer, depth is pooled, the
> target is a parameter. Obstacles 1 and 2 below (global state, temporal state)
> therefore do not apply to a pass modelled on it. Obstacles 3–5 stand.

## If it were attempted

Do not start from `Render12EngineComponent.DrawInternal` — re-entering a whole
frame drags in presentation, upscaling and UI. Start from
`SceneDrawSystem.ExecuteEnvironmentProbeUpdate`. It is the closest existing thing
to the goal: an in-frame, off-main-target, arbitrary-viewpoint render of scene
geometry that the engine already performs and already keeps stable. Read it,
then either imitate its structure or hijack it outright.

A sane order of attack:

1. Instrument `ExecuteEnvironmentProbeUpdate` and `RenderShadowCascades` to learn
   exactly what they save and restore around a foreign-view pass.
2. Reproduce that bookkeeping around a single unlit `DrawUnlit` pass into a
   second `ScreenBuffers`, at low resolution, one frame in ten.
3. Only then worry about lighting, transparency and refresh rate.
4. The blit onto the panel (`src/RttProbe.Logic`) is the last link and already
   written.

Steps 1 and 2 are where this lives or dies, and step 1 is cheap — it is reading,
not building.
